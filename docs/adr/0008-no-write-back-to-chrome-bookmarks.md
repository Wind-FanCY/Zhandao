# 过闸后不写 Chrome 书签，改在数据仓库记已处理清单

过闸之后那条书签必须以某种方式"消失"，否则下次打开过闸页它会重复出现、要求重复判断——而重复判断是**收件箱**堆积的另一种形态（ADR-0002 已将堆积列为本项目主要失效模式）。本项目**不写 Chrome 的书签文件**，而是在 `data/` 中维护一份已处理 URL 清单，读取**收件箱**时据此过滤。

不写书签文件是因为它不安全，证据来自 pre-flight 实测：该文件顶层含 `checksum` 与 `sync_metadata` 两个字段，说明 Chrome 会校验它、且书签正在云端同步；同时 Chrome 运行期间把书签持有在内存中并定期落盘，外部写入会被下一次落盘覆盖。为省一次手动删除，去写一个有校验和、正在同步、且被另一进程持有的文件——风险与收益不成比例。最坏情况是丢书签，而书签夹是这个库唯一的入口。

## Considered Options

- **写回 Chrome 书签，删除已处理条目**：摩擦最低，但有丢失用户书签的风险，且校验和算法属 Chrome 内部实现、无公开承诺。已否决。
- **输出"可删清单"由本人手动在 Chrome 里删**：安全，且可随时叠加在本方案之上，不冲突。等书签夹真的膨胀了再加。
- **在数据仓库记已处理清单并过滤**（已选）。

## Consequences

- **书签夹会无限增长。** 已处理条目仍留在夹子里，只是不再呈现给本人。需偶尔手动清理。
- 已处理清单顺带记录了**本人划掉了什么**。"看过并判定不值得"本身有信息量：它防止三个月后重新收录同一篇，也是判断力的记录。因此该清单存入 `data/` 并纳入版本控制，**不属于 `.cache/`**——它不是 ADR-0003 所说的可随时重建的派生物。
- 过滤依据是 URL。同一内容换了 URL（追踪参数、短链、镜像站）会被判为新条目。**URL 规范化程度是新的开放项。**
