# 实测档案

`CLAUDE.md` 只留**做事之前必须知道的约束**；这里留**为什么是那些约束，以及量过什么、别重复量什么**。

**每条结论都带日期和样本量。** 这不是形式：本项目最贵的教训是同一个结论在不同样本量下会翻面——
同一个改动在 10 条评估集上「勉强站住」、31 条上「站得很稳」、换到 47 篇语料上「退回噪音」。

## 怎么用这份文件

- **想改检索**：先读「检索基线沿革」和「已做过、不要重复的实验」。
- **看到任何百分比**：先确认它的样本量，再决定要不要当真。
- **结论冲突时日期新的胜**；被推翻的旧结论**保留原文并标注**，因为「曾经以为」本身是信息——
  它能挡住下一个人再走一遍。

## 检索基线沿革

三代基线，`k1=1.5` `b=0.75`，整篇**材料**为检索单位。**跨代不可比**：语料规模变了，任务难度也就变了。

```
① 2026-09-16 早   10 条评估集 / 6 篇材料      整体 recall@1=60%  @3= 70%  MRR=0.710
② 2026-09-16 晚   31 条评估集 / 6 篇材料      整体 recall@1=68%  @3= 74%  MRR=0.759
③ 2026-09-16 夜   31 条评估集 / 46 篇材料     整体 recall@1=77%  @3= 84%  MRR=0.815
④ 2026-09-17      31 条评估集 / 49 篇材料     整体 recall@1=71%  @3= 81%  MRR=0.772   ← 当前
```

④ 比 ③ 退步，原因是新增的 3 篇与英文目标材料同语言、共享词汇（见下面专门一节），
**不是**回填关键词造成的（已消融）。

**当前基线（③）的分组视图**——聚合数字会骗人，必须分组看：

```
整体            n=31  recall@1= 77%  @3= 84%  MRR=0.815
含中文材料       n=19  recall@1=100%  @3=100%  MRR=1.000
纯英文材料       n=12  recall@1= 42%  @3= 58%  MRR=0.521   ← 唯一真实缺陷
我猜的查询       n=30  recall@1= 77%  @3= 83%  MRR=0.808
本人真写的速记    n= 1  recall@1=100%                       ← n=1，只看趋势
```

英文目标的排名列表 `[3,1,1,4,1,3,8,17,8,1,40,1]`——**有一条排第 40 名 / 46**。
跨语言 gap 是当前压倒性的第一问题。

**噪音地板**：n=10 时一条查询翻面 = 10 个百分点，n=31 时 = 3.2 个百分点。
所以 ①②③ 三代对「多大的差距算数」的门槛完全不同：①下 20% 以内不算数，③下 6% 以内不算数。

## 被推翻的结论

保留原文，标注为何翻面。**这一节是这份文件存在的主要理由。**

### 1. 「索引时翻译已把纯英文材料 recall@3 提到 100%」 —— 过拟合到 3 个样本

当时（基线①）量到的：

```
             改动前                      改动后
整体        recall@1=60% @3= 70%        recall@1=80% @3=100%   MRR 0.710→0.883
含中文材料   recall@1=86% @3=100%        recall@1=86% @3=100%   不变（对照组）
纯英文材料   recall@1= 0% @3=  0%        recall@1=67% @3=100%   MRR 0.200→0.778
```

英文目标样本从 3 条增到 12 条后重测：

```
纯英文材料      改动前(n=3)  0% / 0%      改动后(n=3)  67% / 100%   ← 当时的结论
                                         重测(n=12)   25% /  33%   ← 真相
```

**正确的说法**：索引时翻译**有效**（它确实把某些英文材料捞进了前三），但**远没有关上跨语言 gap**。

**教训**：3 个样本上的 100% 不是 100%，是「3 个样本都过了」。
当时据此说的「recall@3=100%，给三个候选已经够用」也是错的——第一次真实**归属**就把正确宿主排在第 5 名。
**查询改写（原计划的阶段 3）因此重新回到台面上**，不再是「省掉一整条运行时链路」那么简单。

### 2. 「只用拉丁词项最好」 —— 被否两次

第一次（基线①，n=10）：单条查询从 5/6 拉到 1/6，看着很美，但评估集整体 recall@1 只有 50%。
第二次（基线②，n=31）：崩到 `recall@1=50% @3=50%`，**两个数字相等意味着要么第一名要么完全不出现**
——实测 6 条查询零结果。这正是「三个指标必须一起看」的样子：单看 @1 会把它误判成改进。

### 3. 「丢掉中文单字能提升检索」 —— 小库假象

```
                默认 → 丢单字
 6 篇        68/74 → 81/94     (+13 / +20)   ← 曾据此建议改默认值
47 篇        77/84 → 81/87     (+4  /  +3)   ← 约 1 条查询，在噪音里
```

47 篇下含中文材料反而从 100% 掉到 95%。**决定：不改默认值。** `tokenize` 的单字/二字组开关保留。

### 4. 「长口语句比短问句难检索」 —— 不成立

基线② 的 20 条新样本分两类量：`short` recall@1=64%、`oral` 67%，**无差别**。
`kind` 字段保留在评估集里，样本变多后可重测。

### 5. 「无内容的索引页拖累检索」 —— 没有证据

剔除「图解网络」那篇索引页：recall@1 不变（60%），MRR 仅 0.710→0.725（n=10 下是噪音）。
所以要不要剔除它，**理由只能是定义（它永远答不了任何问题），不能是检索指标**。
后来确实删了，依据是 ADR-0010 的定义。

## 机制定位

### 中文单字词项会把同一段原文记三次分

查询里的「压缩」被 tokenize 切成 `压` + `缩` + `压缩` 三个词项，BM25 对三者分别计分，
于是**中文密集的长文档每命中一个词拿三倍信用，纯英文文档拿一倍**。

词项级分数分解（基线①，那条真实**速记**作查询）：错误的第 1 名命中 **27** 个查询词项、正确宿主只命中 **9** 个。

```
错误第 1 名（性能优化篇，长 7728）贡献前几名：积 10.2% 缩 7.2% 输出 6.9% 压缩 6.6% 输 4.8%
正确宿主（compression，长 1400）贡献前几名：flush 18.7% compression 13.8% write 13.1% 缩 12.7%
```

`积` 贡献最大，而它**根本不是词**——是「累积」的碎片，在那篇长文里出现 9 次。
功能词（所以 / 要么 / 每次）只占 23.2%，**所以主因不是停用词，是单字碎片**。

### 按文档频率过滤停用词也有效，但不如消掉单字

基线① 同一条查询的三档对比：**原样排名 5/6 → 丢弃出现在 ≥50% 文档的词后 2/6 → 只用拉丁词项 1/6**。
这是一个与「单字/二字组开关」不同的旋钮（按 df 过滤 vs 按字形过滤），**尚未在 31 条评估集上测过**。
注意这三个数字是单条查询，n=1。

### N=6 时 IDF 几乎不工作，所以加文档会让检索变好

反直觉但实测如此。41 篇探针语料（抓进临时目录、**没有**写成**材料**），且**全是干扰项**
（31 条评估样本没有一条以它们为答案），所以这是最悲观的加文档情形：

```
                        全部 n=31        含中文 n=19      纯英文 n=12
 6 篇 · 当前默认      @1=68% @3=74%    @1= 95% @3=100%   @1=25% @3=33%
47 篇 · 当前默认      @1=77% @3=84%    @1=100% @3=100%   @1=42% @3=58%
```

机制：6 篇时 IDF 值域只有 `0.074–1.54`，稀有度几乎不参与打分；47 篇时只出现在一两篇里的词项
IDF 大幅拉高，而 `积`、`缩`、`压` 这些单字碎片在 41 篇网络文章里到处都有，IDF 被压下去。
**加文档自动修掉了大半个单字问题。**

探针实验预测 77/84/0.814，真实收录 46 篇后实测 77/84/0.815——**预测成立**。

### 第一次真实归属时三个候选全错（原表）

```
查询 = 速记原文「compression 会累积输出，SSE 连接长期不结束，所以事件永远不到；
                 要么禁压缩，要么每次 write 后 res.flush()」
1. 前端面试刷题必备（性能优化篇）  34.97
2. 45 道 Promise 面试题            29.43
3. 图解网络（小林 coding 索引）     27.67
4. 前端面试刷题必备（手撕代码篇）   24.87
5. expressjs/compression           18.45   ← 正确宿主
6. SSE 规范（WHATWG）               5.53   ← 另一个正确宿主
```

我当时另造了一条短问句作对照（「SSE 事件收不到 compression」），正确宿主排第 4 和第 6，
**同样进不了前三**——所以「速记是长句」不是原因。真正的原因见下。

### 归属候选排错的根因是库太小

那条真实**速记**（compression / SSE）：**6 篇语料里正确宿主排第 5，46 篇语料里排第 1——什么都没改。**

今天从「归属候选全错」出发，查了分词、查了 IDF、查了 Readability，最后答案是库太小。
**现在挡住这个项目的不是技术方案，是库太小。**

### Readability 会把代码块连壳一起吞掉

逐段隔离（xiaolincoding.com，VuePress 生成）：

```
① 原始 DOM              <pre> 3 个
② Readability 之后      <pre> 0 个      ← 它丢的
③ turndown 之后         无代码
④ 跳过 Readability 直接 turndown   代码在   ← turndown 无辜
```

抽取结果里 `socket(` / `bind(` / `AF_INET` / `sockaddr` 各 **0 次**——不是没围栏，是代码不存在了。
41 篇文章全部零围栏。

修法的不退步验证（**最后一行最重要**）：

```
                         修复前              修复后
tcp_no_listen        1950 字符 围栏 0    →  4477 字符 围栏 6
tcp_tw_reuse_close   7063 字符 围栏 0    →  7569 字符 围栏 4
https_rsa            5436 字符 围栏 0    →  5436 字符 围栏 0   本来无 <pre>，不动
掘金 Promise        39035 字符 围栏 244  → 39035 字符 围栏 244  零退步
```

修复后重抓 41 篇：**围栏 0 → 190 个，分布在 25/41 篇**，`sockaddr` 17 次、`AF_INET` 14 次。
**总体量只涨 2.4%**（844KB → 865KB）——单页最多 +129% 是极端样本，别拿那个数字说事。

**恢复代码块对这 31 条查询的检索指标影响为零**（24 个数字一个不差）。
我曾担心「代码塞进大量拉丁标识符会改变中文单字 vs 拉丁词项的平衡」，实测不成立：
恢复的代码是 socket 编程（`sockaddr` / `af_inet` / `bind`），而评估集问的是
Promise / webpack / compression / SSE，**词项零交集**。

## 归属候选排错的真正原因：拿速记原文当查询

2026-09-17，库 49 篇（46 + undici / curl / zsh 三篇代理主题的英文文档）。
那条速记的正确宿主终于在库里了，但候选仍然全错。三条查询、同一个索引：

```
「undici http_proxy proxy environment variable」（英文）   → undici 第 1 名 ✓
「undici 不读 http_proxy 代理」（短中文）                  → undici 第 1 名 ✓
速记原文（长中文，带「所以…那不是系统功能」）              → 连前 12 都进不去 ✗
```

**短中文查询排第一，所以问题不是跨语言，是「拿速记原文当查询」。**
速记里的填充文字（所以 / 需要 / 全部 / 那不是 / 系统功能）切出的中文二字组
被 44 篇中文网络文章大量吸收，把 `undici` / `http_proxy` 的信号淹掉。
这是「中文单字词项把同一段原文记三次分」那个机制在 49 篇规模上的延续。

**昨天否掉的「长口语句更难检索」假设需要修正**：当时用的是**我编的** oral 句子
（n=20，short 64% / oral 67%，无差别），而**本人真写的**速记第一次给出了反例。
两者的区别不在长短，在**填充词的密度**——我编的 oral 句子仍然是「问句」，
真实速记是「陈述现场」，后者带着大量与主题无关的连接词。

**推论（尚未实现）**：归属时应当把**速记**原文交给模型提炼成检索查询，而不是直接拿原文去搜。
调用次数 = **速记**数（极少），不是查询数，所以「查询改写的调用次数太多」这个原始反对理由
在归属这条链路上不成立；且**归属**本身是批量异步动作，不受 ADR-0009 的当场摩擦约束。

### 加同语言的文档会让该语言的检索变差

同一次改动把英文材料从 2 篇加到 5 篇，纯英文目标反而退步：

```
46 篇（英文 2）   纯英文 n=12  recall@1=42%  @3=58%   排名 [3,1,1,4,1,3,8,17,8,1,40,1]
49 篇（英文 5）   纯英文 n=12  recall@1=25%  @3=50%   排名 [3,1,2,5,1,7,10,29,10,2,44,1]
```

**这是对昨天「加文档会让检索变好」那条的重要限定。** 昨天加的 41 篇全是中文，对英文目标是
纯干扰项、且不共享词汇；这次加的 3 篇与目标同语言、共享英文技术词汇，
于是英文词项的 IDF 被摊薄——原先那 2 篇英文材料因为「稀有」而获得的偶然优势消失了。
**机制尚未隔离验证**（没单独测 IDF 变化），但方向明确：**加文档的效果取决于加的是什么文档。**

### 收录时不自动生成关键词，代价是真实发生的

三篇新英文材料（中文占比 0.1–0.3%）落盘时 `keywords_zh` 全为空，
必须记得手动跑 `npm run keywords -- --write`。这是开放项里那条的第二次兑现。

回填本身的消融（**第一版消融是无效的**：那 3 份材料还没进版本控制，
`git stash` 默认不动未跟踪文件，于是 A/B 跑的是同一份数据、数字一模一样。
改成直接剥掉 `keywords_zh` 才测出差别）：

```
有关键词   整体 71% / 81% / 0.772    纯英文 25% / 50% / 0.411
无关键词   整体 71% / 77% / 0.769    纯英文 25% / 42% / 0.404
```

**回填是轻微正面（1 条查询翻面，噪音内），不是退步的原因。**

## 跨语言 gap

首次实测（基线①，10 条 / 6 篇）：

```
中文材料为目标  n=7   recall@1=100%
英文材料为目标  n=3   recall@1=  0%    排名 [3, 5, 5]
```

材料**语言混杂**：`expressjs/compression` 与 `SSE 规范（WHATWG）` 是纯英文（中文占比 0%），
另外几篇中文占 34–54%。而查询与**标注**是中文。中文二字组在纯英文文档里零命中。

当前（基线③，46 篇）仍然是 `含中文 @3=100%` 对 `纯英文 @3=58%`。**这个 gap 只能靠模型解决**：
查询改写或多语言向量。BM25 调参跨不过去，这一点已被两代基线反复确认。

## 切块：按固定标题层级切不可执行

实测 6 篇真实材料，真正的结构层级每篇都不同：

```
Promise 那篇      h4，47 个
手撕代码          h2，11 个
SSE 规范          12292 字符里只有 5 个标题
```

## 抓取实测

### 代理：undici 不读 `http_proxy`

本机把出网流量走本地代理（`http_proxy=http://127.0.0.1:7897`）。`curl` 认这个环境变量，
**Node 的 fetch（undici）不认**——于是需要代理的站点全部 `UND_ERR_CONNECT_TIMEOUT`，
10 秒超时后还会被当成临时失败重试 3 次，白烧 30 秒。

```
不带处理                    ✗ 10.5s  UND_ERR_CONNECT_TIMEOUT
NODE_USE_ENV_PROXY=1        ✓ 1.8s   200  361KB
undici EnvHttpProxyAgent    ✓ 1.7s   200  361KB
```

选**代码内 `setGlobalDispatcher(new EnvHttpProxyAgent())`**，不用环境变量：launchd 定时脚本
（ADR-0004）和测试是另外两条启动路径，环境变量会被忘，而失效是静默的——表现为「这篇抓不到」，
容易误判成网站的问题。

**顺带一个坑**：本机设了 `http_proxy` 之后，`curl localhost:3001` 会被代理拦下返回 502。
调本地服务要加 `--noproxy '*'`。

### 限流：掘金会返回空壳页

掘金等站点在连续请求后返回空壳页——实测 **2492 字节、正文 13 字**，表现为 `too_short`，
与「页面是 JS 渲染」不可区分。所以抓取必须顺序进行、带 1.5 秒间隔、带完整浏览器请求头
（`Accept` / `Accept-Language` / `Referer`）。

### 实际吞吐

```
首批 6 篇（掘金 / GitHub / WHATWG 混合）    7.9s    attempts 全为 1
图解网络 41 篇（xiaolincoding，同一站点）   68–102s  41/41 成功，零限流
```

## 过闸界面的实测教训

**做决定所需的控件必须在默认视图里，只有「想深入看看」的内容才藏在展开后面。**

第一次真实过闸时六个标题一个都没改——不是懒，是标题输入框被放在「展开」面板里，本人根本没看见。
原设计正好反了：**必须设置**的标题被藏起来，而**可选**的正文预览反而是展开的理由。
**可选步骤一旦需要额外点击，在批量流程里就等于不存在。**

第二条：**抓取到的正文必须立刻落盘。** 原实现把结果放在作业内存并在 30 秒后清理，
于是「读完文章再决定」（真实过闸的必然节奏）之后点「留下」直接 400。实测复现：等 35 秒即可。

第三条：**逐条结果必须逐条推送。** `onProgress(done, total, url)` 只报进度、不带结果，
服务端因此在整批跑完前拿不到任何单条结果——界面上就是多条同时卡在「抓取中」。
所以 `extractArticles` 必须提供 `onItem(item)` 回调。

## 方法论教训

### 复算脚本必须先复现已知基线，再相信它的结论

分词消融那张表第一版是错的，两个 bug：
① 评估集的字段叫 `expect`，我写成了 `materialId`，于是全部 10 条算成未命中；
② `keywords_zh` 是 flow 风格行内数组 `["a","b"]`，我按 block 风格解析，全解析成空——
于是对照组算出的是**索引时翻译之前**那条基线（60%/70%），而我差点据此下结论。

**两个 bug 都不报错、都只是让数字变难看。唯一抓住它们的办法就是先要求脚本重现已知基线。**

### 评估集设错会让你去修不该修的东西

我给第二条**速记**设的期望答案是 `expressjs/compression`，但那篇里 `undici` 0 次、`proxy` 0 次
——正确答案根本不在库里。基于这个错误样本我一度得出「BM25 比随机还差」，差点据此论证要上模型。
**建评估样本时必须先 grep 确认正确答案确实存在于目标材料中。**

### 聚合指标会骗人

基线① 的整体 recall@1=60% 是把两个区间（中文 100% 与英文 0%）平均出来的，掩盖了真正的失效模式。
**按目标材料的语言分组看，才发现症结。**

同理，评估集加了 `origin` 字段（`guessed` / `real_note`）并按它分组，
是为了让「查询是我猜的」这道偏差每次跑 eval 都可见——扩充时量到的差距是
原有 10 条（猜的、且是对着库调出来的）@3=100% 对新起草 20 条 @3=65%，**差 35 个百分点**。

### 断言不是检查

同一类问题一天内修过三次，写法不同、本质一样：
`as any`（客户端访问判别联合）→ `as (T)[]`（filter 后去 null）→ `as string`（读 frontmatter
字段，而 YAML 里 `id: 123` 会解析成数字，断言拦不住）。
**grep `as any` 查不到后两种——审查时要连 `as ` 一起看。**
第四次出现在 `write.test.ts`（`yamlLoad(...) as Record<string, unknown>`，5 处），已换成类型守卫。
